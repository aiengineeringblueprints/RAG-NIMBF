# Enterprise RAG Blueprint on RAGBench TechQA: Refusal and Runtime Analysis

Date: 2026-11-10 · Run: `results/Enterprise-RAG/run6` (DGX Spark, `experiments/enterprise-rag-blueprint-rag.yaml`, commit `9d9e843`)

Analysed config: `recursive_cs512_co64 … k10_hybrid-a0.5` (n = 500). Generator
`qwen3.8-27b`, embedder `nomic-embed-text:latest`, hybrid retrieval (alpha 0.5,
fetch-k 50), query refinement and guardrails on, critic `deepseek-v4-flash`.
Results overview of earlier runs: [enterprise-rag-blueprint-results.md](enterprise-rag-blueprint-results.md).

## TL;DR

- `declined_rate` = 0.584 overstates refusals. The phrase heuristic flags normal
  TechQA answers that contain "error", "failed" and similar words. The real
  refusal rate is **~33–38 %** (165–188 of 500).
- The real refusals have two main causes: **the dataset** (~¼ of refusals are
  questions whose documents do not contain the answer) and **chunk-level
  retrieval within the correct documents** (the correct document set is
  retrieved for 91 % of questions, but the relevant sentences often are not).
  A complete retrieval miss explains only 31 refusals (6 % of questions).
- No bug in the framework or the Blueprint causes refusals. The Blueprint's
  strict "answer only from context" prompt turns missing passages into
  refusals. The effect of its LLM query refinement is **not measured yet**.
- Framework measurement gap: RAGBench gets no `gold_doc_id`, so
  `ground_truth_doc_ids` is empty and `hit@k` / `ndcg@k` / `recall@k` are
  meaningless on TechQA.
- Runtime: ~3.5 h per config, of which ~3 h is RAGAS. Same critic and top-k on
  SQuAD take ~35 min. The cost comes from TechQA's long texts, not from the
  Blueprint or a slow critic endpoint.

## 1. `declined_rate` is a phrase heuristic

`declined` comes from `declines()` in `benchmark/answer_match.py`: substring
match against `_DECLINE_PHRASES`. The list was built for the MCP trust question
set and includes `"error"`, `"failed"`, `"unknown"`, `"permission"`,
`"unable to"`, `"not found"`. TechQA is about IBM support errors, so these words
appear in normal answers.

| Count (n = 500) | Value |
|---|---|
| Flagged `declined` | 292 (58 %) |
| … of which match `"error"` | 167 |
| … of which match `"does not contain"` / `"cannot answer"` | 150 / 58 |
| Real refusals (strict regex: "does not contain", "cannot answer", "not provided/mentioned", …) | 165–188 (33–38 %) |
| Reference answers that the heuristic would flag as `declined` | 225 |

False positive example: *"The error occurs because of missing Linux system
libraries … run the installer with `-console`"* is a correct answer.

The metric is designed for datasets with `expected_behavior` labels. On TechQA
it has no meaning.

## 2. Why the real refusals happen

Without a shared corpus (`has_shared_corpus` is `False` for `ragbench`), the
Blueprint adapter indexes each question's documents as one source
`dataset-doc-{i}` (`replace_blueprint_index` in
`examples/enterprise_rag_plugin/adapter.py`). A TechQA question brings 3–5 IBM
documents with ~18,800 characters in total. All 500 document sets share one
Chroma collection. Because of this mapping, the gold document set of question
*i* is `dataset-doc-{i}`, which allows a manual gold-retrieval check. RAGBench
also labels the relevant sentences per question (`all_relevant_sentence_keys`)
and whether the reference is supported by the documents (`adherence_score`).

The samples were matched to `rungalileo/ragbench` `techqa` `train`,
`shuffle(seed=42).select(range(500))` (same order, all questions verified).

### 2.1 Dataset (~¼ of refusals, correct behaviour)

- 71 of 500 questions have **no** relevant sentence in their documents
  (RAGBench label). The Blueprint refused 43 of them, which is correct but is
  scored as a failure.
- The references were generated by GPT-3.5. Only **64 %** are supported by the
  documents (mean `adherence_score` 0.638). For refused questions it is 48 %,
  for answered ones 73 %.
- Only ~6 % of document sentences are relevant (`relevance_score` 0.064).
  Each question is a needle in an ~18.8 k-character haystack.
- Questions repeat title and body ("Why may I receive … ? Why may I receive …").

### 2.2 Chunk-level retrieval within the correct documents (largest share)

| | n | Gold set in top 10 | Gold set at rank 1 | Gold share of the 10 chunks |
|---|---|---|---|---|
| All | 500 | 91 % | 47 % | 32 % |
| Answered | 312 | 96 % | 55 % | 37 % |
| Refused | 188 | 84 % | 34 % | 25 % |
| Refused, gold set missing | 31 | 0 % | 0 % | 0 % |

At 512 characters per chunk, a document set is ~40 chunks; about 3 of the 10
retrieved chunks come from it. Coverage of the RAGBench relevant sentences in
the retrieved context (first 80 characters of each relevant sentence found in
the joined contexts; questions without relevant sentences excluded):

| | n | Mean relevant-sentence coverage | Zero coverage | Full coverage |
|---|---|---|---|---|
| Answered | 284 | 48 % | 39 | 54 |
| Refused | 145 | **19 %** | **66** | 5 |

So the model usually refuses because the decisive passage is missing from the
context, not because the document set is missing. This matches the typical
refusal text: *"The provided context does not contain information regarding X.
The documents primarily discuss Y …"*. Refusal rate is 34.5 % when the gold set
is retrieved and 69 % when it is not.

### 2.3 Blueprint (not yet measured)

- The prompt is strict "answer only from context". With the passage missing, the
  generator refuses instead of giving a partial answer. Sometimes it adds
  "based on general knowledge". For an enterprise RAG this is mostly desired.
- `enterprise_rag_mcp_query_refinement: true` rewrites every question with an
  LLM before retrieval. TechQA questions are long error reports with error
  codes, versions and product names. If the rewrite drops those, passage-level
  retrieval gets worse. **Untested.**

### 2.4 Framework

No defect that causes refusals. Measurement gaps:

- `load_corpus_and_questions` sets `gold_doc_id` only for shared-corpus
  datasets. For `ragbench`, `ground_truth_doc_ids` is empty, so there are no
  gold retrieval metrics.
- The heuristic `hit@k` / `ndcg@k` / `recall@k` (`determine_relevance` in
  `benchmark/custom_metrics.py`) count every context above a cosine threshold as
  relevant: hit@1 = 1.0 and recall@k = k/10 on TechQA. See also the caveats in
  [enterprise-rag-blueprint-results.md](enterprise-rag-blueprint-results.md).
- `declined_rate` (section 1).

## 3. Runtime

Per config (`stage_timings` of `recursive_cs512_co64 … k10`):

| Stage | Seconds |
|---|---|
| `adapter_prepare` (index build) | 148 |
| `external_rag` (Blueprint answers 500 questions) | 1,302 (~22 min) |
| `ragas_eval` | 10,692 (~3 h) |
| `custom_metrics` | 289 |
| `total` | 12,445 (~3.5 h) |

14 configs ≈ 50 h. Comparison with the same critic (`deepseek-v4-flash`) and
top-k 12 on SQuAD (`results/qwen3.8-27b/deepseek-v4-flash/run1`): `ragas_eval`
2,097–2,339 s. Critic tokens per config: 2.1 M input / 146 k output on SQuAD
versus 13.0 M input / 2.1 M output on TechQA (~290 vs ~4,200 output tokens per
question). RAGAS splits answers and references into statements and checks each
one, and context precision makes one call per context (10–12 per question).
So the cost grows with text length and top-k.

The critic endpoint is not the cause: two probe calls from the Spark took 2–4 s
and `deepseek-v4-flash` returned no reasoning tokens. `EVAL_CRITIC_MAX_WORKERS`
was 8.

## 4. Failed config in run6

`semantic_bppercentile95 … k10` failed after 5 min with
`Post "http://127.0.0.1:45249/tokenize": … connection reset by peer`. This is
the Ollama embedding runner (nomic-embed), probably a crash. Re-run only that
config after the current worker has finished. The worker skips configs marked
`completed` in `progress.json`, and the config hash must stay the same
(unchanged manifest and checkout):

Use `scripts/run_blueprint_rag.sh`: it exports `RAG_ADAPTER_MODULES`,
`ENTERPRISE_RAG_BLUEPRINT_PATH`, `VECTORDB_DIR`, `INDEX_NAME`, `MCP_ENABLED` and
`HF_HUB_DISABLE_XET`. Calling `python -m benchmark.worker` directly in a fresh
shell fails with `Unsupported RAG_SYSTEM_ADAPTER='enterprise_rag_mcp'` because
the plugin module is not loaded. Set `LOG` so the script does not overwrite the
original `~/bp-rag-run6.log`:

```bash
cd ~/source/Benchmarking-Framework
ollama ps   # check that Ollama is healthy
LOG=~/bp-rag-run6-retry.log scripts/run_blueprint_rag.sh results/Enterprise-RAG/run6
```

## 5. Next steps

Ordered by value per effort.

1. **Re-run the failed semantic k10 config** (section 4) once run6 has
   finished. ~3.5 h.
2. **Gold metrics for RAGBench** (framework):
   - Set `gold_doc_id` for datasets without a shared corpus as well, matching the
     adapter's source IDs (`dataset-doc-{i}`, or better a stable ID used by both
     the framework and the adapter). This fills `ground_truth_doc_ids` and enables
     `custom_retrieval_metrics_mode: gold_doc`.
   - New metric `relevant_sentence_recall`: share of RAGBench
     `all_relevant_sentence_keys` sentences contained in the retrieved contexts.
     Replaces the heuristic `hit@k` on TechQA and measures passage-level
     retrieval, the main refusal cause.
   - Keep `adherence_score` and "has relevant sentences" as sample metadata.
     Report metrics on the answerable subset as well (or add a filter knob, e.g.
     `dataset_require_relevant_sentences`).
   - Each knob with a `BenchmarkConfig` field, env fallback and a test in
     `tests/test_config.py`.
3. **Fix `declined_rate`** (framework):
   - Do not report `declined_rate` for datasets without `expected_behavior`, or
   - use the existing LLM judge (`make_decline_judge`,
     `enterprise_rag_mcp_decline_judge`), and
   - remove ambiguous phrases (`"error"`, `"failed"`, `"unknown"`,
     `"permission"`) from `_DECLINE_PHRASES` or apply them only to short answers.
4. **Ablation to split the refusal causes** (100 questions,
   `RAGAS_ENABLED=false`, `CUSTOM_METRICS_ENABLED=true`, fixed chunking
   `recursive` 1024/128, top-k 10, nomic):
   1. Blueprint as now (baseline)
   2. Blueprint with `enterprise_rag_mcp_query_refinement: false` → effect of the
      query rewrite
   3. Blueprint with `enterprise_rag_mcp_guardrails: false` → effect of the input
      check
   4. Internal pipeline with the same chunking, embedder, hybrid retrieval and
      top-k → Blueprint vs framework pipeline

   Compare the real refusal rate, `relevant_sentence_recall` and gold hit@k. Log
   the refined queries of the Blueprint for refused questions with gold-set hits
   to check for lost error codes and versions.
5. **Retrieval improvements**, depending on step 4: larger chunks (1024/2048 are
   already better in run5), a reranker on the 50 hybrid candidates, lower
   `retrieval_hybrid_alpha` (more BM25 weight for error codes), deduplicate the
   TechQA corpus (duplicate documents under different IDs, see the results
   overview).
6. **Shorten eval runtime**:
   - Raise `EVAL_CRITIC_MAX_WORKERS` from 8 to 16–24 if the coassist.de endpoint
     allows it (roughly linear speedup).
   - Use `sample_size` 150–200 for chunking sweeps and re-run only the best
     configs with 500.
   - Add a knob to select RAGAS metrics (none exists in `config.py`); context
     precision is the largest cost at top-k 10–12.
